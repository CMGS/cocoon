## 1. Overview

### 1.1 Motivation

This document defines a **VM-native OCI image format** for Cocoon where kernel, rootfs, and user customizations are stored as separate OCI layers. The design achieves three goals:

1. **Registry-native deduplication**: Kernel and rootfs layers from the same base cloud image are content-identical across builds, shared in any OCI-compliant registry via content-addressable storage. Only per-user customization layers differ.
2. **Fast direct-kernel boot**: The extracted kernel and initrd bypass UEFI firmware entirely, eliminating firmware initialization overhead and enabling faster cold boot.
3. **OverlayFS + virtiofs rootfs**: Instead of reconstructing a qcow2 disk image from OCI tar layers, layers are extracted as directories and composed via Linux OverlayFS. The merged filesystem is served to the guest via virtiofs, providing instant layer composition with per-VM copy-on-write semantics.

### 1.2 Relationship to docs/04

[docs/04-oci-conversion.md](./04-oci-conversion.md) (Status: Implemented) covers the conversion of OCI **container** images to bootable qcow2 disk images via Buildah extraction and guestfish partitioning. That pipeline remains unchanged and continues to serve users who start from container images with pre-installed bootloaders.

This document **extends** OCI support with a new image format purpose-built for VMs. Instead of converting an opaque container rootfs into a disk image, the OCI VM image format splits a cloud image into discrete, content-addressable layers (kernel, rootfs, customization) that can be independently cached, shared, and composed.

### 1.3 Relationship to docs/11

[docs/11-bootable-oci-build.md](./11-bootable-oci-build.md) (Status: Planned) covers how to **build base bootable images from scratch** -- distro-specific package requirements, Dockerfile examples, the `docker build` -> `cocoon image pull` -> `cocoon image verify` pipeline, and the Phase 2 `cocoon image build-bootable` helper. The Cocoonfile mechanism defined in [section 4](#4-user-customization-cocoonfile) of this document supersedes the build *process* outlined in docs/11 (Cocoonfile replaces manual Dockerfiles for customization). The remaining guidance content in docs/11 (minimum requirements by distro, Dockerfile templates, verification, cloud image workarounds, cocoon-ready.service) is complementary and maintained independently.

### 1.4 Terminology

| Term | Meaning |
|------|---------|
| **Cloud image** | Traditional VM disk image (qcow2/raw) with UEFI bootloader (GRUB/systemd-boot), kernel, and full OS. Used in Phase 1. |
| **Bootable OCI image** | Generic term: any OCI container image whose rootfs contains components needed to boot a VM. Umbrella term covering both formats below. |
| **UEFI-rootfs OCI image** | Phase 1 format: OCI image containing a full disk layout with ESP partition, GRUB/systemd-boot, kernel, and rootfs. Converted to qcow2 for UEFI boot via CLOUDHV.fd. Uses standard OCI layer media types. |
| **OCI VM Image** | Phase 2 format: OCI image with custom Cocoon media types, separate kernel/initrd/rootfs layers, and a config blob. Booted via direct kernel boot (CH `payload.kernel`). Defined in this document. |
| **Base image** | The source qcow2 (Phase 1) or extracted OCI cache (Phase 2) that VMs are created from. Shared via copy-on-write overlays. |

> **Note**: When this document says "OCI VM image" it always refers to the Phase 2 direct-boot format. The Phase 1 UEFI path is documented in [docs/04-oci-conversion.md](./04-oci-conversion.md).

## 2. OCI Image Format

### 2.1 Media Types

The OCI VM image format uses custom media types to distinguish VM layers from standard container layers:

| Layer | Media Type | Description |
|-------|-----------|-------------|
| Config blob | `application/vnd.cocoon.vm.config.v1+json` | VM configuration (arch, resources, kernel cmdline) |
| Kernel layer | `application/vnd.cocoon.vm.kernel.v1.tar` | Contains vmlinuz + initrd |
| Rootfs layer | `application/vnd.cocoon.vm.rootfs.v1.tar` | Root filesystem (everything except kernel/initrd) |
| Customization layer | `application/vnd.cocoon.vm.rootfs.v1.tar` | User modifications (same media type as rootfs, applied on top) |

The customization layer reuses the rootfs media type intentionally -- it represents the same kind of content (filesystem tree) and is applied as an overlay on top of the base rootfs.

### 2.2 Config Blob Schema

The config blob carries VM-specific metadata that does not exist in standard OCI container configs:

```json
{
  "arch": "amd64",
  "default_cpus": 2,
  "default_memory_mb": 2048,
  "kernel_cmdline": "console=hvc0 root=PARTUUID=<uuid> ro quiet",
  "kernel_path": "/vmlinuz",
  "initrd_path": "/initrd.img",
  "virtiofs_tag": "cocoon-rootfs",
  "rootfs_partuuid": "<uuid>",
  "labels": {"maintainer": "user@example.com"}
}
```

| Field | Type | Description |
|-------|------|-------------|
| `arch` | string | Target architecture (`amd64`, `arm64`) -- values from Go's `runtime.GOARCH` |
| `default_cpus` | int | Default vCPU count for `cocoon create` |
| `default_memory_mb` | int | Default memory in MB for `cocoon create` |
| `kernel_cmdline` | string | Kernel command line passed to Cloud Hypervisor. Format: `console=hvc0 root=PARTUUID=<uuid> ro quiet` where `<uuid>` is the GPT PARTUUID detected from the image. |
| `kernel_path` | string | Path to vmlinuz within the kernel layer tar |
| `initrd_path` | string | Path to initrd within the kernel layer tar |
| `virtiofs_tag` | string | virtiofs filesystem tag (`cocoon-rootfs`) used in the guest `root=` parameter and Cloud Hypervisor `fs[]` config |
| `rootfs_partuuid` | string | (Optional) Actual GPT PARTUUID detected from the cloud image's root partition via `guestfish part-get-gpt-guid`. Used in `kernel_cmdline` as `root=PARTUUID=<uuid>`. Omitted when the image has no GPT partition table. |
| `labels` | map[string]string | (Optional) User-defined labels from Cocoonfile `LABEL` directives. Omitted when no labels are set. |

### 2.3 Layer Structure

An OCI VM image consists of two or more layers, ordered as follows:

- **Layer 1 (kernel)**: Contains `vmlinuz` + `initrd.img` extracted from the cloud image `/boot` directory. Media type: `application/vnd.cocoon.vm.kernel.v1.tar`. Fixed position, mandatory.
- **Layer 2 (rootfs)**: Remaining filesystem from the cloud image -- everything except the kernel and initrd files. Media type: `application/vnd.cocoon.vm.rootfs.v1.tar`. Fixed position, mandatory.
- **Layer 3..N (customization, optional)**: User modifications produced by Cocoonfile builds. Media type: `application/vnd.cocoon.vm.rootfs.v1.tar`. Each layer represents a separate customization applied in order on top of the rootfs. Multiple Cocoonfile builds can be chained, each adding one customization layer.

> **v1 Status**: The current implementation always produces exactly two layers (kernel + rootfs). Cocoonfile `RUN`/`COPY` steps modify the rootfs in-place before extraction, so the result is still a 2-layer image. Customization layers (3..N) as separate deltas are a planned optimization.

The first two layers MUST follow this specification (kernel and rootfs). Additional layers are user customizations applied in order -- layer 3 is applied first on top of rootfs, layer 4 on top of that, and so on.

### 2.4 Deduplication Model

The layer split exploits the fact that many teams build from the same base cloud image but add different applications:

- Same base cloud image produces **content-identical** layers 1 and 2 across all builds, because the kernel/rootfs content is deterministic for a given cloud image version.
- Only customization layers (3..N) differ per user build.
- OCI registries store layers by content-addressable digest. Identical layers are stored once regardless of how many manifests reference them.

**Example**: 10 teams building from `ubuntu-22.04` cloud image, each adding their own application via Cocoonfile. Some teams chain multiple customization layers (e.g., a shared middleware layer + a team-specific app layer):

```
Registry storage:
  1 kernel layer        (shared, ~50 MB)
  1 rootfs layer        (shared, ~800 MB)
  1 middleware layer     (shared by 4 teams, ~120 MB)
  10 app-specific layers (unique per team, varies)
  10 OCI manifests      (one per team)

  Team A manifest: kernel + rootfs + middleware + app-A   (4 layers)
  Team B manifest: kernel + rootfs + app-B                (3 layers)
  Team C manifest: kernel + rootfs + middleware + app-C   (4 layers)

Total unique storage: ~850 MB base + 1 middleware + 10 app layers
Without deduplication: 10 x ~1 GB = ~10 GB
```

### 2.5 Compression and Registry Compatibility

**Current convention**: All Cocoon VM layers use uncompressed `.tar` media types (e.g., `application/vnd.cocoon.vm.kernel.v1.tar`, `application/vnd.cocoon.vm.rootfs.v1.tar`). No gzip or zstd compression suffix is applied at the layer level.

**Rationale**: Uncompressed tars simplify the initial implementation. Registry transport (HTTP) already applies its own compression, so layer-level compression would double-compress in many cases. Additionally, the kernel and initrd layers are small (typically <100 MB), and even rootfs layers are modest compared to container images with large application dependencies. The implementation cost of compression/decompression logic is not justified at this stage.

**Compressed variants (future)**: If transfer size or registry compatibility becomes an issue, compressed media types should follow the OCI naming convention by appending the compression algorithm as a suffix:

- `application/vnd.cocoon.vm.rootfs.v1.tar+gzip`
- `application/vnd.cocoon.vm.rootfs.v1.tar+zstd`
- `application/vnd.cocoon.vm.kernel.v1.tar+gzip`
- `application/vnd.cocoon.vm.kernel.v1.tar+zstd`

The pull process would detect the suffix and decompress before extracting to the local cache. The cache always stores uncompressed directory trees regardless of the wire format.

**Registry compatibility**: Some registries may reject pushes containing unknown media types. Mitigation strategies, in order of preference:

1. **OCI 1.1+ `artifactType`**: Set the `artifactType` field in the OCI manifest to `application/vnd.cocoon.vm.image.v1`. Registries that support OCI 1.1+ artifacts will accept arbitrary media types under this model.
2. **Annotation fallback**: Use standard `application/vnd.oci.image.layer.v1.tar` as the layer media type but annotate each layer descriptor with `org.cocoon.layer.type=kernel`, `org.cocoon.layer.type=rootfs`, or `org.cocoon.layer.type=customization`. This sacrifices type-level distinction but is compatible with all registries.
3. **Testing matrix**: Validate push/pull against Docker Hub, GitHub Container Registry (ghcr.io), Harbor, and Quay.io. Document any registry-specific workarounds.

**Phase 2 decision**: Start with uncompressed `.tar` and custom media types. Add gzip support and the annotation fallback only if registry compatibility or transfer size becomes a concrete issue during testing.

## 3. Build Process (`cocoon image build`)

### 3.1 Input

| Input | Required | Description |
|-------|----------|-------------|
| Cloud image | Yes | qcow2 or raw `.img` format cloud image file |
| Cocoonfile | No | Dockerfile-like file for user customizations (see [section 4](#4-user-customization-cocoonfile)) |
| `--tag <ref>` | No | OCI reference name (e.g., `myregistry.io/myvm:latest`) |

### 3.2 Build Steps

```
Cloud Image (qcow2/raw)
    |
    v
1. Mount read-only via guestfish
    |
    v
2. Detect kernel in /boot (see S3.3)
    |
    v
3. Detect matching initrd in /boot (see S3.3)
    |
    v
4. Extract kernel + initrd -> kernel layer tar archive
    |
    v
5. Read root partition PARTUUID from GPT
   (guestfish part-get-gpt-guid /dev/sda 2)
    |
    v
6. Extract remaining rootfs (excluding /boot/vmlinuz-*, /boot/initrd*)
   -> rootfs layer tar
    |
    v
7. Build OCI config blob with kernel_cmdline, paths, PARTUUID
    |
    v
8. Assemble OCI manifest and push to local store
```

Step 5 uses `guestfish part-get-gpt-guid /dev/sda 2` to read the existing PARTUUID from the cloud image's GPT partition table. This PARTUUID is stored in the config blob and used in the kernel cmdline for device-name-independent root device identification.

### 3.3 Kernel Detection Logic

The build process must locate the highest-version kernel and its matching initrd from the cloud image's `/boot` directory:

```
1. List /boot/vmlinuz-* (or /boot/vmlinuz if no versioned files; ARM: /boot/Image)
2. Sort by version number (e.g., 5.15.0-100 > 5.15.0-91), pick highest
3. Match initrd by same version suffix:
   - /boot/initrd.img-{version} (Debian/Ubuntu)
   - /boot/initramfs-{version}.img (RHEL/Fedora)
4. Error if no kernel found: "no kernel found in /boot; cloud image may not be bootable"
```

The version sorting uses numeric comparison on each segment separated by `.` and `-`, so that `5.15.0-100` correctly sorts higher than `5.15.0-91`.

### 3.4 PARTUUID Strategy

The root partition is identified by PARTUUID rather than device name (e.g., `/dev/sda2`) to survive disk reordering across different VM configurations.

**GPT cloud images** (typical case):
- Read existing PARTUUID from cloud image GPT: `guestfish part-get-gpt-guid /dev/sda 2`
- Store PARTUUID in OCI config blob `rootfs_partuuid` field

**MBR-only cloud images** (legacy):
- Read the 32-bit MBR disk signature from the master boot record (bytes 440–443)
- Synthesize PARTUUID in Linux's native MBR format: `{8-hex-disk-sig}-{2-digit-partnum}`
  (e.g., `a1b2c3d4-02` for disk signature `0xa1b2c3d4`, partition 2)
- The Linux kernel natively supports `root=PARTUUID=<sig>-<partnum>` for MBR partitions
  (see kernel `block/partitions/msdos.c` — `blkdev_parts_gen_uuid`)

**Rationale**: `root=PARTUUID=<uuid>` is device-name-independent. Unlike `/dev/sda2` or `/dev/vda2`, a PARTUUID remains stable regardless of how the hypervisor enumerates disks.

**Note on virtiofs path**: The OCI virtiofs boot path does **not** use PARTUUID -- there is no block device. The guest kernel mounts the root filesystem via `root=cocoonfs rootfstype=virtiofs`, which references the virtiofs tag rather than a partition UUID. However, the build process still records the cloud image's PARTUUID in the config blob `rootfs_partuuid` field. This preserves the option to fall back to block-device boot (e.g., qcow2 reconstruction) without requiring a rebuild.

### 3.5 Deterministic Tar Rules

Content-addressable layer deduplication ([section 2.4](#24-deduplication-model)) requires that two builds from the same source cloud image produce **identical layer digests**. This is only possible if tar archive creation is fully deterministic.

**Why this matters**: If tar creation is non-deterministic -- file ordering varies by filesystem enumeration order, timestamps reflect build-time wall clock, metadata differs across machines -- then the same cloud image built on different hosts produces different SHA-256 digests for the kernel and rootfs layers. This defeats the deduplication model entirely: registries would store N copies of semantically identical layers because their digests differ.

**Required rules for tar archive creation**:

| Property | Rule |
|----------|------|
| **File ordering** | Lexicographic sort of full paths (e.g., `/bin/bash` before `/etc/hostname` before `/usr/lib/libz.so`). The sort is byte-order on UTF-8 encoded paths. |
| **Timestamps** | All `mtime` values normalized to a fixed epoch: `1970-01-01T00:00:00Z` (Unix epoch zero). Alternatively, the image creation timestamp from the OCI config blob may be used, but epoch zero is simpler and avoids coupling tar content to config metadata. `atime` and `ctime` are set to the same value. |
| **Ownership** | UID/GID preserved as-is from the source filesystem. Do not normalize to 0:0 -- correct ownership is important for guest operation (e.g., system services running as non-root users). |
| **Permissions** | File mode bits preserved as-is from the source filesystem. |
| **Extended attributes** | `xattr` values preserved if present. This is important for SELinux security labels (`security.selinux`) and file capabilities (`security.capability`). |
| **ACLs** | Stripped from tar headers. POSIX ACLs are not commonly needed in VM images and are not portable across tar implementations. If ACL support is needed in the future, it can be added as an opt-in flag. |
| **Whiteout files** | Standard OCI `.wh.` whiteouts not used. Base layers (kernel, rootfs) are complete archives with no parent layer to delete from. Customization layers use OverlayFS-native whiteouts (0/0 char devices) for deletions (see note below). |
| **Symlinks** | Preserved as symlinks (not dereferenced). The tar entry records the link target path. |
| **Device nodes** | Preserved. Character and block device nodes may be present in rootfs images (e.g., `/dev/null`, `/dev/console`). |
| **Hard links** | Preserved. If multiple paths reference the same inode, subsequent entries are recorded as tar hard links to the first entry. |

> **Customization Layer Deletion Semantics**: Unlike base layers, customization layers produced by Cocoonfile builds ([section 4](#4-user-customization-cocoonfile)) represent a delta from the base rootfs. File deletions in Cocoonfile `RUN` steps are represented using **OverlayFS-native whiteout files** (character device `0/0`), which are archived directly from the OverlayFS upperdir. This is distinct from OCI whiteout convention (`.wh.` prefix files). Cocoon's layer composition uses host-side OverlayFS, not OCI union filesystem semantics, so OverlayFS-native whiteouts are the correct representation. Tools that inspect these layers outside of Cocoon should be aware of this convention.

**Implementation**: Use Go's `archive/tar` with explicit header normalization before writing each entry. Pseudocode for the normalization step:

```go
func normalizeHeader(hdr *tar.Header) {
    hdr.ModTime = time.Unix(0, 0)   // epoch zero
    hdr.AccessTime = time.Unix(0, 0)
    hdr.ChangeTime = time.Unix(0, 0)
    hdr.Format = tar.FormatPAX      // deterministic header format
    // UID, GID, Mode, Xattrs, Linkname: preserved as-is
    // Remove any ACL xattrs (system.posix_acl_access, system.posix_acl_default)
    delete(hdr.PAXRecords, "SCHILY.acl.access")
    delete(hdr.PAXRecords, "SCHILY.acl.default")
}
```

**Verification**: A future `cocoon image build --reproducible` flag will verify determinism by building the same cloud image twice (with independent filesystem walks) and comparing the resulting layer digests. If the digests differ, the build fails with a diagnostic message identifying the first divergent tar entry. This flag is intended for CI pipelines, not routine use.

### 3.6 Build Progress Output

`cocoon image build` writes Docker-like step progress to stderr during the build pipeline. Each major phase is reported as a numbered step with optional detail lines showing key artifacts:

```
Step 1/8 : Detecting kernel...
 ---> 5.15.0-100-generic
Step 2/8 : Extracting kernel and initrd...
Step 3/8 : Building kernel layer...
 ---> sha256:abc123def456
Step 4/8 : Reading PARTUUID...
 ---> 12345678-1234-1234-1234-123456789abc
Step 5/8 : Extracting rootfs...
Step 6/8 : Building rootfs layer...
 ---> sha256:789012345678
Step 7/8 : Assembling OCI layout...
 ---> sha256:fedcba987654
Step 8/8 : Saving tag...
 ---> my-image:v1
```

The `Step N/M :` prefix follows the Docker build output convention. Detail lines prefixed with ` ---> ` show computed values (kernel version, layer digests, PARTUUID, tag name). All progress output goes to stderr so that stdout remains clean for machine-parseable output (e.g., the final `Built:` / `Digest:` lines). The progress writer is implemented in `oci/progress.go`.

### 3.7 Layer Deduplication (Shared Blob Store)

All blobs produced during a build -- the config blob, kernel layer, rootfs layer, and OCI manifest -- are stored in the shared content-addressed blob store at `cache/oci/blobs/sha256/`. The per-tag OCI layout under `cache/oci/layouts/{hash16}/` contains hardlinks pointing back to the shared store rather than independent copies.

```
cache/oci/
+-- blobs/sha256/
|   +-- aaa111...    # kernel layer (shared across builds from same base)
|   +-- bbb222...    # rootfs layer (shared across builds from same base)
|   +-- ccc333...    # config blob (build A)
|   +-- ddd444...    # config blob (build B)
|   +-- eee555...    # manifest (build A)
|   +-- fff666...    # manifest (build B)
+-- layouts/
    +-- 7f3a.../     # Build A layout
    |   +-- blobs/sha256/
    |       +-- aaa111...  -> hardlink to ../../blobs/sha256/aaa111...
    |       +-- bbb222...  -> hardlink to ../../blobs/sha256/bbb222...
    |       +-- ccc333...  -> hardlink to ../../blobs/sha256/ccc333...
    |       +-- eee555...  -> hardlink to ../../blobs/sha256/eee555...
    +-- 9b2d.../     # Build B layout
        +-- blobs/sha256/
            +-- aaa111...  -> hardlink to ../../blobs/sha256/aaa111...
            +-- bbb222...  -> hardlink to ../../blobs/sha256/bbb222...
            +-- ddd444...  -> hardlink to ../../blobs/sha256/ddd444...
            +-- fff666...  -> hardlink to ../../blobs/sha256/fff666...
```

In this example, builds A and B share the same kernel and rootfs layers (same base cloud image), so the `aaa111...` and `bbb222...` blobs exist once in the shared store with hardlinks from both layouts. The `BlobStore` (implemented in `oci/blobstore.go`) handles blob storage, existence checks, and hardlink creation. If hardlinking fails (e.g., cross-device), it falls back to a regular copy.

**Reference tracking**: The `db/oci-layer-refs.json` file maps each blob digest to the manifest digests that reference it, along with the blob size and creation timestamp. This mapping is updated during builds (when blobs are added) and consulted during garbage collection (to determine which shared blobs have zero references and can be removed). The file is protected by `db/oci-layer-refs.lock`.

### 3.8 Migration from cache/oci-builds/

When Cocoon starts and detects the old `cache/oci-builds/` directory, `MigrateOCICache()` (implemented in `oci/migrate.go`) performs a one-time migration:

1. For each tag in `oci-build-tags.json` whose layout path points to the old `cache/oci-builds/` location:
   - Copies blobs from the old layout into the shared blob store (`cache/oci/blobs/sha256/`)
   - Creates a new layout directory under `cache/oci/layouts/` with hardlinks to the shared blobs
   - Copies non-blob files (`oci-layout`, `index.json`) to the new layout
   - Updates the tag index to point to the new layout path
   - Registers blob references in `oci-layer-refs.json`
2. After all tags are migrated, the old `cache/oci-builds/` directory is removed.

The migration is idempotent: layouts already in the new location are skipped. If the old directory does not exist, migration is a no-op.

## 4. User Customization (`Cocoonfile`)

### 4.1 Syntax

Cocoonfile uses Dockerfile-like syntax for familiarity:

```dockerfile
FROM ubuntu-noble-cloudimg-amd64.img
RUN apt-get update && apt-get install -y nginx
COPY ./app /opt/app
LABEL version="1.0"
```

The `FROM` directive specifies the base cloud image as a local file path. Download the cloud image first, then reference it in the Cocoonfile. Support for FROM referencing OCI VM images (enabling chain builds) is planned for a future release.

**Future**: Each Cocoonfile build will add one customization layer on top of existing layers, enabling chained builds where the output of one build becomes the `FROM` base for the next. This layer accumulation (3, 4, 5, etc.) is a planned feature.

### 4.2 Build Mechanism

The Cocoonfile build process leverages existing container build infrastructure:

**Current v1 implementation:**
1. Parse Cocoonfile using Cocoon's built-in line-by-line parser (`oci/cocoonfile.go`). Supported directives: `FROM`, `RUN`, `COPY`, `LABEL`.
2. Create a writable copy of the base cloud image
3. Execute `RUN` and `COPY` instructions via `virt-customize` against the writable copy
4. Re-extract the full rootfs from the modified image as a deterministic tar
5. Package as a two-layer OCI image (kernel + rootfs) with the standard media types

**Planned optimization (future):**
1. Mount the rootfs layer and any existing customization layers (from the base OCI VM image) as the build context base filesystem
2. Execute `RUN` and `COPY` instructions via `virt-customize` against the image
3. Compute the delta (changed files) between the original filesystem state and the modified state
4. Package the delta as a new customization layer with media type `application/vnd.cocoon.vm.rootfs.v1.tar`
5. The kernel layer (layer 1) and all preceding layers are carried forward unchanged from the base image. Only the new customization layer is created.

### 4.3 Dependencies

Building Cocoonfile support requires the following dependencies:

| Dependency | Purpose |
|------------|---------|
| `github.com/google/go-containerregistry` | OCI manifest/layer manipulation, registry push/pull |
| `virt-customize` (from libguestfs-tools) | Required for executing Cocoonfile `RUN` and `COPY` steps |

## 5. Pull Process (`cocoon image pull --oci` — Phase 2 Planned)

> **Phase 2 — Planned**: This section describes functionality that is not yet implemented. The pull process for OCI VM images will be added in Phase 2.

### 5.1 Registry Pull

1. Pull the OCI manifest from the registry using `go-containerregistry`
2. Verify that layer media types match the expected cocoon VM types (see [section 2.1](#21-media-types))
3. Pull layers by digest -- registry deduplication ensures shared layers are transferred only once

If media type verification fails, the pull aborts with a permanent error indicating the image is not a valid Cocoon OCI VM image.

### 5.2 Local Cache Extraction

After pulling, layers are extracted into a local cache directory keyed by manifest digest:

```
{cache}/oci/{manifest-digest}/
+-- manifest.json
+-- config.json
+-- vmlinuz          # From kernel layer
+-- initrd.img       # From kernel layer
+-- rootfs/          # Rootfs layer extracted as directory tree
+-- custom-1/        # First customization layer (if present)
+-- custom-2/        # Second customization layer (if present)
+-- ...              # Additional customization layers as needed
```

The kernel and initrd are extracted as standalone files (not inside a tar) for direct use by Cloud Hypervisor's `payload.kernel` and `payload.initramfs` fields. The rootfs and customization layers are extracted as directory trees (not kept as tars) for use as OverlayFS lowerdirs. Customization directories are numbered in layer order: `custom-1/` corresponds to OCI layer 3, `custom-2/` to layer 4, and so on.

### 5.3 Layer Extraction

Layers are extracted as directory trees for OverlayFS composition. No qcow2 reconstruction, guestfish, or qemu-img is required:

```
1. Extract kernel layer tar -> vmlinuz + initrd.img (standalone files)
2. Extract rootfs layer tar -> rootfs/ directory tree
3. For each customization layer (in order):
   Extract customization tar -> custom-{N}/ directory tree
```

All extracted directories in the cache are **read-only** and **shared** across VMs. Per-VM copy-on-write is handled by OverlayFS at boot time (see [section 8](#8-storage-layout)).

When composing the OverlayFS stack, the `lowerdir` parameter lists directories from top to bottom (rightmost is lowest):

```
lowerdir=custom-N:...:custom-2:custom-1:rootfs
```

For example, an image with two customization layers:

```
lowerdir=custom-2:custom-1:rootfs
```

All customization directories and the rootfs directory are read-only lowerdirs. File lookups proceed from left to right: a file in `custom-2` shadows the same path in `custom-1`, which shadows the same path in `rootfs`.

### 5.4 Cache Key

The OCI manifest digest serves as the cache key:

- Re-pull with the same digest results in a cache hit; layer extraction is skipped entirely
- Cache invalidation happens only when the manifest digest changes (i.e., any layer was modified)
- The cache directory structure under `{cache}/oci/{manifest-digest}/` is self-contained (directories, not qcow2 files) and can be garbage-collected independently

## 6. Boot Process (Direct Kernel + virtiofs)

> **Phase 2 — Planned**: This section describes functionality that is not yet implemented. Direct kernel boot with virtiofs rootfs delivery will be added in Phase 2.

### 6.1 Cloud-Hypervisor REST API Payload

For OCI VM images, Cocoon uses **direct kernel boot** via Cloud Hypervisor's `payload.kernel` field and **virtiofs** for the root filesystem. The CH REST API requires both the `payload` (kernel/initrd/cmdline) and `fs[]` (virtiofs configuration):

```json
{
  "payload": {
    "kernel": "/var/lib/cocoon/cache/oci/{digest}/vmlinuz",
    "initramfs": "/var/lib/cocoon/cache/oci/{digest}/initrd.img",
    "cmdline": "root=cocoonfs rootfstype=virtiofs rw console=ttyS0,115200n8 console=hvc0"
  },
  "fs": [
    {
      "tag": "cocoonfs",
      "socket": "/var/lib/cocoon/vms/{vmID}/virtiofsd.sock",
      "num_queues": 1,
      "queue_size": 1024
    }
  ]
}
```

The `cmdline` value is read from the OCI config blob's `kernel_cmdline` field. The `kernel` and `initramfs` paths point to the extracted files in the OCI cache directory. The `fs[]` entry configures virtiofs to serve the OverlayFS-merged root filesystem to the guest.

### 6.2 virtiofsd Lifecycle

Before issuing the Cloud Hypervisor VM create/boot API call, Cocoon must spawn a `virtiofsd` process for the VM:

1. Mount OverlayFS for the VM (see [section 8](#8-storage-layout) for the mount command)
2. Spawn `virtiofsd` with `--shared-dir` pointing to the merged mount point and `--socket-path` matching the `fs[].socket` in the CH config
3. Wait for the virtiofsd socket to become available
4. Issue the CH REST API `vm.create` + `vm.boot` calls

The virtiofsd process runs for the lifetime of the VM and is terminated when the VM is stopped or deleted. See [docs/17-volume-passthrough.md](./17-volume-passthrough.md) for virtiofsd lifecycle management details.

### 6.3 No Firmware Required

Direct kernel boot bypasses UEFI entirely:

- **No `CLOUDHV.fd` needed**: The firmware file is not loaded, not referenced, and does not need to be present on the system for OCI VM images.
- **Faster boot**: The kernel loads immediately without firmware initialization, UEFI variable storage setup, or bootloader chain (UEFI -> GRUB -> kernel).
- **No block device for rootfs**: The root filesystem is served via virtiofs from the host OverlayFS mount, eliminating the need for qcow2 disk reconstruction.
- **Kernel + initrd sourced from OCI cache**: The kernel and initrd come from the OCI kernel layer, not from a disk image's `/boot` directory.

### 6.4 Boot Detection

Boot detection for OCI VM images uses the **same serial log pattern matching** as firmware-booted VMs:

- Login prompt detection via serial console output (`login:` pattern)
- The `--boot-timeout` flag applies identically -- if the login prompt is not detected within the timeout period, the boot is considered failed

No changes to the boot detection logic are required. The detection mechanism is agnostic to how the kernel was loaded (firmware vs. direct).

### 6.5 Initramfs Requirements for virtiofs Root (Phase 2 Planned)

> **Note**: This section describes the **Phase 2 planned** virtiofs root boot path. The current v1 implementation uses `root=PARTUUID=<uuid>` (standard block device). The kernel cmdline `root=cocoonfs rootfstype=virtiofs` is a **Cocoon-specific convention** that will be used when direct kernel boot is implemented. Stock distribution initramfs images (dracut, initramfs-tools) do not natively support virtiofs as a root filesystem type. The custom `cocoon-virtiofs` dracut module (described below) provides the early-mount logic required to handle this cmdline parameter. Images built without this module will fail to boot.

**The Problem**: The Phase 2 direct kernel boot path will use `root=cocoonfs rootfstype=virtiofs` in the kernel cmdline, which requires the guest initramfs to understand virtiofs root mounting. (The current v1 implementation uses `root=PARTUUID=<uuid>` with standard block device boot — see [section 2.2](#22-config-blob-schema).) Stock cloud-image initramfs images (built by dracut or initramfs-tools) typically handle only block device roots (`/dev/sdX`, `PARTUUID=`, `UUID=`). They may not include the `virtiofs` kernel module or the early-userspace mount logic needed to mount a virtiofs filesystem as `/sysroot` before pivot_root.

**Required initramfs capabilities**:

- The `virtiofs` kernel module must be loaded (or built-in to the kernel) before the root mount attempt. Without it, the kernel cannot register the `virtiofs` filesystem type.
- Early mount logic must execute `mount -t virtiofs cocoonfs /sysroot` (or equivalent) instead of the standard block device mount. The mount source (`cocoonfs`) matches the `virtiofs_tag` in the OCI config blob and the `fs[].tag` in the Cloud Hypervisor config.
- The `9p` kernel module SHOULD be included as an optional fallback for environments where virtiofs is unavailable (e.g., older hypervisors or debugging scenarios).

**Approach A (Recommended for Phase 2 v1)**: `cocoon image build` generates a custom initramfs during the build process. After extracting the kernel and stock initramfs from the cloud image, the build step invokes dracut to regenerate the initramfs with virtiofs support:

```bash
dracut --force --add-drivers "virtiofs 9p 9pnet 9pnet_virtio" \
       --install "mount" \
       --add "cocoon-virtiofs" \
       /boot/initrd-cocoon.img $(uname -r)
```

The `cocoon-virtiofs` dracut module provides a custom mount hook that detects the `rootfstype=virtiofs` cmdline parameter and performs the virtiofs root mount. The original cloud-image initramfs is replaced in the OCI kernel layer with this regenerated version. This ensures every OCI VM image has a known-good initramfs regardless of the source cloud image's initramfs configuration.

**Approach B (Alternative)**: Require cloud-image builders to include virtiofs support in their initramfs. `cocoon image verify` inspects the initramfs (via `lsinitrd` or guestfish inspection of the initrd archive) and checks for the presence of the `virtiofs.ko` module. If the module is missing, verification fails with an actionable error:

```
ERROR: initramfs does not contain virtiofs module.
       Rebuild initramfs with: dracut --add-drivers "virtiofs" --force
```

This approach avoids modifying the cloud image's initramfs but shifts responsibility to the image builder, which may lead to a poor out-of-box experience.

**Validation**: Regardless of approach, `cocoon image verify` SHOULD check that the initramfs embedded in the OCI kernel layer contains virtiofs support. For Approach A, this is a sanity check on the build output. For Approach B, this is the primary gate. The check inspects the initramfs archive for `virtiofs.ko` (or `virtiofs.ko.zst`, `virtiofs.ko.xz` for compressed modules).

**Fallback design note**: If virtiofs root mounting proves too fragile across distro initramfs variants, the alternative architecture is to use a block device root (qcow2 or raw overlay attached as a virtio-blk disk) with virtiofs used only for additional mounts (user data, shared volumes). This would simplify the initramfs contract (standard block device root) but would lose the layered-rootfs benefit (no OverlayFS composition of OCI layers as the root filesystem). The block device fallback is tracked as a contingency; the `rootfs_partuuid` field in the config blob ([section 2.2](#22-config-blob-schema)) is retained specifically to support this path without requiring a rebuild.

### 6.6 Security Model: Rootfs-Serving virtiofsd

**Distinction from user-volume virtiofsd**: The OCI boot path spawns a virtiofsd instance that serves the guest's *entire root filesystem* via the OverlayFS merge directory ([section 6.2](#62-virtiofsd-lifecycle)). This is fundamentally different from the user-volume virtiofsd described in [docs/17-volume-passthrough.md](./17-volume-passthrough.md), which serves user-selected host directories with configurable allowlists and read-only defaults. The rootfs virtiofsd has no allowlist -- it serves whatever is in the OverlayFS merge tree, including all binaries, libraries, and configuration files that constitute the guest OS.

**Threat model**:

- **Guest escape via virtiofsd**: A compromised guest could exploit vulnerabilities in virtiofsd (e.g., path traversal, FUSE protocol bugs) to access host files outside the shared directory. Mitigation: `--sandbox=chroot` confines virtiofsd's filesystem view to the OverlayFS merge directory. Even if the guest achieves arbitrary FUSE request crafting, the virtiofsd process itself is chrooted and cannot access host paths outside the merge tree.
- **Blast radius**: Because the shared directory IS the entire guest rootfs (the OverlayFS merge of lowerdirs + upperdir), a successful escape from the chroot would expose the OverlayFS tree on the host -- specifically the read-only cache directories (`cache/oci/{digest}/rootfs/`, `cache/oci/{digest}/custom-N/`) and the per-VM upper directory (`vms/{vmID}/upper/`). It would NOT expose the entire host filesystem, assuming the chroot sandbox is intact.
- **Write scope**: Guest writes land in the OverlayFS upperdir (`vms/{vmID}/upper/`). The lowerdir cache is read-only at the OverlayFS level. A guest cannot corrupt the shared base image layers.

**Hardening requirements**:

1. virtiofsd MUST run with `--sandbox=chroot`. This is non-negotiable for the rootfs-serving instance (same requirement as user-volume virtiofsd per [docs/17 section 8.6](./17-volume-passthrough.md)).
2. virtiofsd SHOULD run in a dedicated mount namespace (`unshare -m`) to prevent the OverlayFS mount from appearing in the host's global mount table. This limits information leakage and prevents other processes from interacting with the mount.
3. The OverlayFS mount SHOULD use `nosuid,nodev` mount options on the host side to prevent the guest from creating setuid binaries or device nodes that could be exploited if the mount is accessed from the host context.
4. virtiofsd's built-in seccomp filter SHOULD be enabled (it is enabled by default in Rust virtiofsd v1.7+). The seccomp profile restricts the system calls available to the virtiofsd process, reducing the attack surface for kernel exploits.
5. **UID/GID mapping**: The rootfs virtiofsd runs as root on the host because full filesystem access is required to serve the guest rootfs faithfully (ownership, permissions, special files). This means guest root (UID 0) maps to host root. Future work could use user namespaces (`--sandbox=namespace` + `--uid-map`) to remap guest root to an unprivileged host UID, but this requires careful testing to ensure all guest OS operations (package install, service management, device access) work correctly under remapped UIDs.

**Comparison with user-volume virtiofsd**: The user-volume virtiofsd ([docs/17 section 8](./17-volume-passthrough.md)) validates host paths against an allowlist, defaults to read-only, and serves user-specified directories. The rootfs virtiofsd does NOT use the host path allowlist because the shared path is an internal Cocoon-managed directory (the OverlayFS merge point), not a user-specified path. The rootfs virtiofsd is always read-write (the guest must be able to write to its own root filesystem). The security boundary relies on the chroot sandbox and OverlayFS isolation rather than path allowlists.

**Open questions for Phase 2**:

- Whether to run the rootfs virtiofsd as non-root using user namespace UID remapping (adds complexity, may break guest OS operations that assume real root)
- Whether to add MAC (AppArmor or SELinux) confinement profiles for the rootfs virtiofsd process, restricting it to only the OverlayFS merge directory and its socket
- Whether the rootfs virtiofsd should use `--sandbox=namespace` instead of `--sandbox=chroot` for stronger isolation (namespace sandbox adds user namespace + mount namespace on top of chroot)

### 7.2 Flag Semantics (Phase 2 Planned)

The `--oci` flag will explicitly select the OCI VM image code path:

- **With `--oci`**: Image reference is resolved as an OCI VM image. Boot strategy is automatically set to direct kernel boot. No firmware is loaded.
- **Without `--oci`**: Image is treated as a direct cloud image (qcow2/raw) or URL. Boot strategy is automatically set to UEFI. `CLOUDHV.fd` firmware is loaded.

The boot strategy is **auto-determined** based on the presence of `--oci`. There is no user-facing `--boot-strategy` flag.

### 7.3 Phase 2 Considerations: OCI Image Identification

A key design question for Phase 2 is how Cocoon distinguishes cloud images (qcow2 with UEFI boot) from OCI VM images (direct kernel boot + virtiofs). Three approaches were evaluated:

**Option A: Explicit `--oci` flag (recommended)**. The user passes `--oci` to signal the image is an OCI VM image. This is the current approach. It is simple, unambiguous, and requires no image introspection. The trade-off is that the user must know which image type they are using, but this aligns with the principle that image format is a deliberate choice (like choosing between a container image and a VM image).

**Option B: Image metadata inspection (recommended as optional enhancement)**. OCI VM images built by `cocoon image build` include custom media types (see [section 2.1](#21-media-types)) and a config blob with `application/vnd.cocoon.vm.config.v1+json`. When pulling from a registry, Cocoon could inspect the manifest media types to auto-detect OCI VM images without requiring `--oci`. Additionally, a standard OCI annotation such as `org.cocoon.boot-strategy=direct` on the manifest could serve as a lightweight signal. This would enable `cocoon create registry.io/myvm:latest` to auto-select the correct boot path.

**Option C: Content-based detection (not recommended)**. During image pull or conversion, inspect OCI layers for the presence of kernel/initramfs files (suggesting direct boot) vs. bootloader binaries (suggesting UEFI). While this is the most automatic approach, it is fragile: an image could contain both a kernel and a bootloader, or a kernel layer could be packed differently than expected. Content heuristics are unreliable for a boot-path decision that must be correct.

**Decision**: Phase 2 will use **Option A** (explicit `--oci` flag) as the primary mechanism, with **Option B** (media type inspection) as an optional enhancement. When `--oci` is not passed but the resolved manifest contains Cocoon VM media types, Cocoon will auto-detect and use direct kernel boot. This provides a smooth UX for registry-based workflows while preserving explicit control. Option C is rejected due to fragility.

In Phase 1, the `--oci` flag is hidden and returns an error (`"OCI VM images are not yet supported"`), preventing users from accidentally entering the unimplemented code path. Phase 2 will unhide the flag and wire it to the OCI VM image pipeline.

## 8. Storage Layout

```
/var/lib/cocoon/
+-- cache/
|   +-- images/              # Existing: qcow2 base images (non-OCI path)
|   +-- oci/                 # OCI VM image cache (shared blob store + per-tag layouts)
|   |   +-- blobs/sha256/    # Shared content-addressed blob store
|   |   |   +-- {hex}        # Blob files (config, kernel layer, rootfs layer, manifest)
|   |   +-- layouts/         # Per-tag OCI layouts (blobs are hardlinks to shared store)
|   |       +-- {hash16}/    # Layout directory keyed by tag hash
|   |           +-- oci-layout
|   |           +-- index.json
|   |           +-- blobs/sha256/{hex}  # Hardlinks to ../../blobs/sha256/{hex}
|   +-- manifests/           # Existing: OCI manifest cache
+-- db/
|   +-- oci-build-tags.json  # Tag index: tag -> layout path mapping
|   +-- oci-build-tags.lock
|   +-- oci-layer-refs.json  # Blob reference tracking: blob digest -> [manifest digests]
|   +-- oci-layer-refs.lock
+-- firmware/                # Existing: CLOUDHV.fd (UEFI only, not used by OCI path)
+-- vms/
    +-- {vmID}/
        +-- upper/           # NEW: OverlayFS upperdir (per-VM COW writes)
        +-- work/            # NEW: OverlayFS workdir (kernel internal)
        +-- merged/          # NEW: OverlayFS mount point -> virtiofsd serves this
        +-- virtiofsd.sock   # NEW: virtiofsd socket for this VM
```

The OCI build cache uses a **shared blob store** architecture. All blobs (config, kernel layer, rootfs layer, manifest) are stored once in `cache/oci/blobs/sha256/`, keyed by their SHA-256 digest. Per-tag OCI layouts under `cache/oci/layouts/` contain hardlinks to the shared blobs rather than copies. This enables content-level deduplication across builds -- multiple images sharing the same kernel or rootfs layer store the blob once. See [section 3.7](#37-layer-deduplication-shared-blob-store) for details.

The OverlayFS mount command for a VM with two customization layers:

```bash
mount -t overlay overlay \
  -o lowerdir=/var/lib/cocoon/cache/oci/{digest}/custom-2:/var/lib/cocoon/cache/oci/{digest}/custom-1:/var/lib/cocoon/cache/oci/{digest}/rootfs,\
upperdir=/var/lib/cocoon/vms/{vmID}/upper,\
workdir=/var/lib/cocoon/vms/{vmID}/work \
  /var/lib/cocoon/vms/{vmID}/merged
```

Key points:

- The `cache/oci/blobs/sha256/` directory is the shared content-addressed blob store. All blob data (config, kernel layer, rootfs layer, manifest) lives here exactly once, regardless of how many tags reference it.
- The `cache/oci/layouts/{hash16}/` directories contain per-tag OCI layouts. The blobs inside each layout's `blobs/sha256/` subdirectory are **hardlinks** to the shared blob store, not copies. This means a layout removal only decrements the hardlink count; the blob data persists as long as at least one reference exists.
- `db/oci-layer-refs.json` maps blob digests to the manifest digests that reference them. This reference count is used by GC to determine which shared blobs are safe to remove.
- Per-VM state under `vms/{vmID}/` includes OverlayFS directories (`upper/`, `work/`, `merged/`) that provide copy-on-write semantics. Guest writes land in `upper/`, leaving the shared cache untouched.
- The `virtiofsd.sock` socket is the communication channel between Cloud Hypervisor and the virtiofsd daemon serving the merged filesystem.
- The existing `cache/images/`, `cache/manifests/`, and `firmware/` directories are unchanged.

### 8.1 OCI Cache Lifecycle and Garbage Collection

Phase 1 garbage collection ([docs/06-concurrency.md](./06-concurrency.md), [docs/05-storage-management.md](./05-storage-management.md)) uses `references.json` to track per-VM references to base qcow2 images, a global GC lock to prevent races, and a strict lock ordering hierarchy. Phase 2 OCI VM images introduce a new cache tree (`cache/oci/{manifest-digest}/`) and per-VM OverlayFS state that are NOT covered by the existing Phase 1 GC framework. This section defines the lifecycle and garbage collection design for these new objects.

**New objects introduced by the Phase 2 OCI path**:

| Object | Location | Lifetime | Shared? |
|--------|----------|----------|---------|
| OCI layer cache | `cache/oci/{manifest-digest}/` (kernel, initrd, rootfs, custom dirs) | Persists until all referencing VMs are deleted AND GC runs | Yes, across all VMs from the same OCI image |
| Per-VM OverlayFS upperdir | `vms/{vm-id}/upper/` | VM lifetime (create to delete) | No, per-VM |
| Per-VM OverlayFS workdir | `vms/{vm-id}/work/` | VM lifetime (create to delete) | No, per-VM |
| Per-VM OverlayFS mount | `vms/{vm-id}/merged/` | VM runtime (start to stop) | No, per-VM |
| Rootfs virtiofsd socket | `/var/lib/cocoon/vms/{vm-id}/virtiofsd.sock` | VM runtime (start to stop) | No, per-VM |

> **Socket location note**: The **rootfs-serving** virtiofsd socket listed above (`virtiofsd.sock`) lives under `/var/lib/cocoon/vms/{vm-id}/` alongside the OverlayFS mount it serves (persistent, per [docs/05 SSOT](./05-storage-management.md)). **Volume-passthrough** virtiofsd sockets (`virtiofs-{tag}.sock`) are a separate concern, living under `/run/cocoon/vms/{vm-id}/` (ephemeral, see [docs/17](./17-volume-passthrough.md)).

**Reference counting for OCI cache**: Reference counting uses `/var/lib/cocoon/db/oci-references.json` with a corresponding `/var/lib/cocoon/db/oci-references.lock` (see [docs/05-storage-management.md](./05-storage-management.md) Phase 2 SSOT). This file maps manifest digests to referencing VM IDs:

```json
{
  "sha256:abc123...": {
    "refs": ["vm-01HXYZ...", "vm-01HABC..."],
    "created": "2026-02-15T10:30:00Z"
  },
  "sha256:def456...": {
    "refs": ["vm-01HDEF..."],
    "created": "2026-02-16T14:00:00Z"
  }
}
```

Reference lifecycle:
- **VM create from OCI image**: Add `vm-id` to the manifest digest's `refs` array. If the manifest digest entry does not exist, create it (this happens after layer extraction during `cocoon image pull --oci` or `cocoon create --oci`).
- **VM delete**: Remove `vm-id` from the manifest digest's `refs` array. If the array becomes empty, the OCI cache directory is eligible for GC (but not immediately deleted -- GC runs separately).
- **cocoon gc**: Scan `oci-references.json` for entries with empty `refs` arrays and remove the corresponding `cache/oci/{manifest-digest}/` directories.

**Lock ordering** (extending the Phase 1 hierarchy from [docs/06-concurrency.md](./06-concurrency.md)):

```
Level 1: GC Lock (global)                          # Existing
    |
Level 2: Reference Counter Lock (global)            # Existing (for qcow2 refs)
Level 2: OCI Build Tag Lock (global)                # Protects oci-build-tags.json — Implemented
Level 2: OCI Layer Refs Lock (global)               # Protects oci-layer-refs.json — Implemented
Level 2: OCI Reference Lock (global, new)           # Protects oci-references.json — Phase 2
Level 2: Name Index Lock (global)                   # Existing
    |
Level 3: Image Conversion Lock (per-checksum)       # Existing
Level 3: OCI Cache Lock (per-manifest-digest, new)  # Protects cache/oci/{digest}/ during extraction
    |
Level 4: VM Metadata Lock (per-VM)                  # Existing
```

The OCI Reference Lock is at the same level as the existing Reference Counter Lock -- they protect different files and are never held simultaneously. The per-digest OCI Cache Lock prevents concurrent layer extractions for the same manifest digest (same pattern as the per-checksum Image Conversion Lock for qcow2 images).

**GC criteria**:

1. An OCI cache entry (`cache/oci/{manifest-digest}/`) is safe to remove when: (a) zero VM references in `oci-references.json`, AND (b) no active `cocoon image pull --oci` or `cocoon create --oci` conversion is in progress for that digest (checked via the per-digest OCI Cache Lock -- if the lock is held, skip this entry).
2. Per-VM OverlayFS cleanup on `cocoon delete`: unmount the OverlayFS at `vms/{vm-id}/merged/` first (if mounted), then remove `upper/`, `work/`, and `merged/` directories. The unmount MUST precede directory removal to avoid "device busy" errors.
3. Rootfs virtiofsd socket (`/var/lib/cocoon/vms/{vm-id}/virtiofsd.sock`) is cleaned up when the virtiofsd process exits (VM stop or delete). Stale sockets from crashed processes are removed during reconciliation or at next VM start. Volume virtiofsd sockets under `/run/cocoon/vms/{vm-id}/` are ephemeral and handled separately (see [docs/17](./17-volume-passthrough.md)).

**Integration with existing `cocoon gc` command**: The `cocoon gc` command currently scans `references.json` for unreferenced qcow2 base images. It MUST be extended to also:
- Scan `oci-references.json` for unreferenced OCI cache entries
- Remove `cache/oci/{manifest-digest}/` directories for entries with zero references and no active extraction lock
- Report OCI cache entries in the GC summary output (e.g., "Removed 3 unreferenced OCI cache entries, freed 2.4 GB")

**Crash consistency**: If `cocoon delete` crashes after removing the VM's reference from `oci-references.json` but before cleaning up `vms/{vm-id}/upper/`, the next `cocoon gc` or reconciliation pass will detect the orphaned VM directory (VM ID not found in any `config.json`) and clean it up. This follows the same crash recovery pattern used for Phase 1 qcow2 overlays.

## 9. Boot Strategy Simplification

With OCI VM images, the boot strategy model is simplified to two modes, auto-selected based on image source:

| Image Source | Boot Strategy | Firmware | Kernel Source | Rootfs | Selection |
|---|---|---|---|---|---|
| Cloud image (qcow2) | UEFI | CLOUDHV.fd (`payload.firmware`) | From disk (UEFI loads grub/kernel) | qcow2 block device | Auto: no `--oci` flag |
| OCI VM image | Direct + virtiofs | None | From OCI layer (`payload.kernel`) | virtiofs root (OverlayFS merged) | Auto: `--oci` flag present |

### 9.1 Changes to Boot Strategy Types

- `BootStrategyPVH` is **removed entirely**. PVH boot was an alternative firmware-based approach that added complexity without sufficient benefit over UEFI for the cloud image path.
- The `BootStrategy` type becomes a two-value enum: `"uefi"` | `"direct"` (internal only, auto-selected based on `--oci` flag).
- No user-facing `--boot-strategy` flag is needed. The choice is implicit:
  - `cocoon create myimage.qcow2 ...` uses UEFI
  - `cocoon create --oci myregistry.io/myvm:latest ...` uses direct kernel boot

### 9.2 Rationale

The two boot strategies map cleanly to the two image sources. Users do not need to understand boot strategy internals -- they choose an image format, and the boot method follows automatically.

## 10. Kernel Pinning (Trade-off)

### 10.1 Design Decision

**Kernel version is locked at `cocoon image build` time.**

The kernel used to boot the VM comes from the OCI kernel layer, which was extracted from the cloud image during `cocoon image build`. It does **not** come from the rootfs disk image's `/boot` directory.

### 10.2 Implications

- Guest-side `apt upgrade linux-image-*` installs a new kernel to the rootfs `/boot` directory but has **no effect** on boot. The VM continues to boot with the kernel from the OCI kernel layer.
- To upgrade the kernel: re-run `cocoon image build` with an updated cloud image. This produces a new kernel layer with the updated kernel.
- This matches the **container model**: images are immutable artifacts. Upgrade means rebuild and redeploy, not in-place mutation.

### 10.3 Benefits

- **Reproducibility**: The kernel version is deterministic for a given OCI manifest digest. Two VMs created from the same OCI VM image always boot the same kernel.
- **Auditability**: The kernel version is recorded in the build result. `cocoon image inspect <ref>` shows the OCI config blob metadata (arch, kernel cmdline, virtiofs tag) for locally built OCI VM images.
- **Rollback safety**: Rolling back to a previous OCI VM image version also rolls back the kernel, eliminating kernel/userspace version skew.

## 11. Compatibility Matrix

| Source Image | Boot Method | Firmware | Kernel Source | Rootfs Delivery | Registry |
|---|---|---|---|---|---|
| Cloud image (qcow2/URL) | UEFI | CLOUDHV.fd | Loaded from disk by bootloader | qcow2 block device | N/A |
| OCI container image | UEFI | CLOUDHV.fd | Loaded from disk by bootloader | qcow2 (converted from rootfs) | Container registry |
| OCI VM image (this doc) | Direct kernel + virtiofs | None | Extracted from OCI kernel layer | virtiofs (OverlayFS merged from layers) | Container registry |

**Row 1** (Cloud image): The existing default path. Users download a cloud image, Cocoon boots it via UEFI. No registry involved.

**Row 2** (OCI container image): The [docs/04](./04-oci-conversion.md) pipeline. Cocoon pulls a container image, converts it to qcow2, boots via UEFI. Requires a bootloader (GRUB) pre-installed in the container image.

**Row 3** (OCI VM image): This document. Cocoon builds or pulls an OCI VM image with separate kernel/rootfs/customization layers, extracts them as directories, composes them via OverlayFS, and serves the merged filesystem to the guest via virtiofs. Direct kernel boot, no bootloader or block device required.

## 13. VMConfig Schema Extension for OCI VM Images

This section documents how `VMConfig` (`types/config.go`) evolves for OCI VM images while maintaining backward compatibility with Phase 1 qcow2-based VMs.

### 13.1 New Field: `image_type`

```go
ImageType string `json:"image_type,omitempty"` // "qcow2" (default) or "oci-vm"
```

The `omitempty` tag ensures Phase 1 configs (which lack this field) are treated as `"qcow2"` by default.

### 13.2 Field Groups by Image Type

| Field | qcow2 (Phase 1) | oci-vm (Phase 2) |
|-------|-----------------|------------------|
| `base_key` | `{checksum_16}_{arch}` | Not used |
| `firmware_path` | `/var/lib/cocoon/firmware/CLOUDHV.fd` | Not used |
| `boot_strategy` | `"uefi"` | `"direct"` |
| `overlay_path` | `overlay.qcow2` | Not used |
| `manifest_digest` | Not used | `sha256:abc123...` |
| `oci_cache_key` | Not used | Digest pointing to `cache/oci/{digest}/` |
| `kernel_path` | Not used | Path to extracted vmlinuz |
| `initramfs_path` | Not used | Path to extracted initrd.img |
| `cmdline` | Not used | Kernel command line |

### 13.3 Mutual Exclusivity

- **qcow2 branch**: `firmware_path` is set; `kernel_path`/`initramfs_path`/`cmdline` are empty.
- **oci-vm branch**: `kernel_path`/`initramfs_path`/`cmdline` are set; `firmware_path` is empty.

This is enforced at VM creation time. `cocoon inspect` displays only the relevant fields for the image type.

### 13.4 SchemaVersion Strategy

`SchemaVersion` stays at **1**. The new fields use `omitempty`, making the extension purely additive — no existing config.json needs rewriting. If a future change requires incompatible structural modifications (e.g., renaming fields or changing semantics), bump to `SchemaVersion: 2` with a migration function in `config.Migrate()` that reads v1 and writes v2.

### 13.5 Backward Compatibility

Phase 1 VMs with missing `image_type` field default to `"qcow2"` and work unchanged. No config rewrite occurs. The `image_type` field is written only for new VMs created with `--oci` (Phase 2).

### 13.6 Warm-Start Interaction

Checkpoint metadata ([docs/15](./15-warm-start.md)) inherits `image_type` from the source VMConfig:
- **qcow2 checkpoints**: `base_key` identifies the backing image.
- **oci-vm checkpoints**: `manifest_digest` replaces `base_key` as the provenance identifier. The checkpoint restore path must verify the OCI cache entry still exists before restoring.

## 14. OverlayFS Layer Limits and Squashing

### 14.1 Kernel Limits

Linux OverlayFS supports up to **500 lowerdirs** since kernel 5.11+ (commit `d9b4943`). Earlier kernels (pre-5.11) had a practical limit of approximately 128 layers, bounded by the mount options string fitting in a single page. The `mount(2)` options string also has a kernel-dependent length limit (typically 4096 bytes).

### 14.2 Cocoon Recommendation

**Maximum 32 customization layers** for OCI VM images (33 total lowerdirs including the rootfs base). This provides ample flexibility for typical image customization workflows while staying well within kernel limits and keeping mount options strings manageable.

### 14.3 Validation

`cocoon image pull --oci` validates layer count during manifest parsing, **before** downloading layer blobs:

```
ERROR: OCI VM image has 47 customization layers (maximum: 32).
Reduce layers by squashing at build time:
  buildah commit --squash <container> <image>
```

### 14.4 Squashing at Build Time

Cocoon does **NOT** perform runtime squashing — it is the image builder's responsibility. Standard OCI tooling supports this:

```bash
# Squash all layers into one during commit
buildah commit --squash <container> <image>

# Or minimize layers in Cocoonfile by combining RUN directives
```

### 14.5 Performance Note

Each lowerdir adds a path lookup in the OverlayFS resolution chain. For **positive lookups** (file exists), the overhead is minimal since the kernel returns the first hit. For **negative lookups** (file not found), the kernel must traverse all layers, which scales linearly with layer count.

For latency-sensitive workloads, **1–5 customization layers** are recommended. The dentry cache mitigates repeated lookups but cold-cache scenarios (first access after mount) will incur the full traversal cost.
