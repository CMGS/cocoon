## 1. Overview

### 1.1 Motivation

This document defines a **VM-native OCI image format** for Cocoon where kernel, rootfs, and user customizations are stored as separate OCI layers. The design achieves three goals:

1. **Registry-native deduplication**: Kernel and rootfs layers from the same base cloud image are content-identical across builds, shared in any OCI-compliant registry via content-addressable storage. Only per-user customization layers differ.
2. **Fast direct-kernel boot**: The extracted kernel and initrd bypass UEFI firmware entirely, eliminating firmware initialization overhead and enabling faster cold boot.
3. **OverlayFS + virtiofs rootfs**: Instead of reconstructing a qcow2 disk image from OCI tar layers, layers are extracted as directories and composed via Linux OverlayFS. The merged filesystem is served to the guest via virtiofs, providing instant layer composition with per-VM copy-on-write semantics.

### 1.2 Relationship to docs/04

[docs/04-oci-conversion.md](./04-oci-conversion.md) (Status: Implemented) covers the conversion of OCI **container** images to bootable qcow2 disk images via Buildah extraction and guestfish partitioning. That pipeline remains unchanged and continues to serve users who start from container images with pre-installed bootloaders.

This document **extends** OCI support with a new image format purpose-built for VMs. Instead of converting an opaque container rootfs into a disk image, the OCI VM image format splits a cloud image into discrete, content-addressable layers (kernel, rootfs, customization) that can be independently cached, shared, and composed.

### 1.3 Supersedes docs/11

[docs/11-bootable-oci-build.md](./11-bootable-oci-build.md) (Status: Planned) is a placeholder document for bootable OCI build guidance. The Cocoonfile mechanism defined in [section 4](#4-user-customization-cocoonfile) of this document supersedes the build process outlined in docs/11. The remaining guidance content (verified images, cloud image workarounds) in docs/11 is unaffected and can be updated independently.

## 2. OCI Image Format

### 2.1 Media Types

The OCI VM image format uses custom media types to distinguish VM layers from standard container layers:

| Layer | Media Type | Description |
|-------|-----------|-------------|
| Config blob | `application/vnd.cocoon.vm.config.v1+json` | VM configuration (arch, resources, kernel cmdline) |
| Kernel layer | `application/vnd.cocoon.vm.kernel.v1.tar` | Contains vmlinuz + initrd |
| Rootfs layer | `application/vnd.cocoon.vm.rootfs.v1.tar` | Root filesystem (everything except kernel/initrd) |
| Customization layer | `application/vnd.cocoon.vm.rootfs.v1.tar` | User modifications (same media type as rootfs, applied on top) |

The customization layer reuses the rootfs media type intentionally -- it represents the same kind of content (filesystem tree) and is applied as an overlay on top of the base rootfs.

### 2.2 Config Blob Schema

The config blob carries VM-specific metadata that does not exist in standard OCI container configs:

```json
{
  "arch": "x86_64",
  "default_cpus": 2,
  "default_memory_mb": 2048,
  "kernel_cmdline": "root=cocoonfs rootfstype=virtiofs rw console=ttyS0,115200n8 console=hvc0",
  "kernel_path": "/vmlinuz",
  "initrd_path": "/initrd.img",
  "virtiofs_tag": "cocoonfs",
  "rootfs_partuuid": "00000000-0000-0000-0000-000000000002"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `arch` | string | Target architecture (`x86_64`, `aarch64`) |
| `default_cpus` | int | Default vCPU count for `cocoon create` |
| `default_memory_mb` | int | Default memory in MB for `cocoon create` |
| `kernel_cmdline` | string | Kernel command line passed to Cloud Hypervisor. Uses `root=cocoonfs rootfstype=virtiofs` for virtiofs root mount. |
| `kernel_path` | string | Path to vmlinuz within the kernel layer tar |
| `initrd_path` | string | Path to initrd within the kernel layer tar |
| `virtiofs_tag` | string | virtiofs filesystem tag used in the guest `root=` parameter and Cloud Hypervisor `fs[]` config |
| `rootfs_partuuid` | string | Root partition PARTUUID from the original cloud image GPT. Retained for potential fallback to block-device boot; not used in the virtiofs path. |

### 2.3 Layer Structure

An OCI VM image consists of two or more layers, ordered as follows:

- **Layer 1 (kernel)**: Contains `vmlinuz` + `initrd.img` extracted from the cloud image `/boot` directory. Media type: `application/vnd.cocoon.vm.kernel.v1.tar`. Fixed position, mandatory.
- **Layer 2 (rootfs)**: Remaining filesystem from the cloud image -- everything except the kernel and initrd files. Media type: `application/vnd.cocoon.vm.rootfs.v1.tar`. Fixed position, mandatory.
- **Layer 3..N (customization, optional)**: User modifications produced by Cocoonfile builds. Media type: `application/vnd.cocoon.vm.rootfs.v1.tar`. Each layer represents a separate customization applied in order on top of the rootfs. Multiple Cocoonfile builds can be chained, each adding one customization layer.

The first two layers MUST follow this specification (kernel and rootfs). Additional layers are user customizations applied in order -- layer 3 is applied first on top of rootfs, layer 4 on top of that, and so on.

### 2.4 Deduplication Model

The layer split exploits the fact that many teams build from the same base cloud image but add different applications:

- Same base cloud image produces **content-identical** layers 1 and 2 across all builds, because the kernel/rootfs content is deterministic for a given cloud image version.
- Only customization layers (3..N) differ per user build.
- OCI registries store layers by content-addressable digest. Identical layers are stored once regardless of how many manifests reference them.

**Example**: 10 teams building from `ubuntu-22.04` cloud image, each adding their own application via Cocoonfile. Some teams chain multiple customization layers (e.g., a shared middleware layer + a team-specific app layer):

```
Registry storage:
  1 kernel layer        (shared, ~50 MB)
  1 rootfs layer        (shared, ~800 MB)
  1 middleware layer     (shared by 4 teams, ~120 MB)
  10 app-specific layers (unique per team, varies)
  10 OCI manifests      (one per team)

  Team A manifest: kernel + rootfs + middleware + app-A   (4 layers)
  Team B manifest: kernel + rootfs + app-B                (3 layers)
  Team C manifest: kernel + rootfs + middleware + app-C   (4 layers)

Total unique storage: ~850 MB base + 1 middleware + 10 app layers
Without deduplication: 10 x ~1 GB = ~10 GB
```

## 3. Build Process (`cocoon image build`)

### 3.1 Input

| Input | Required | Description |
|-------|----------|-------------|
| Cloud image | Yes | qcow2 or raw `.img` format cloud image file |
| Cocoonfile | No | Dockerfile-like file for user customizations (see [section 4](#4-user-customization-cocoonfile)) |
| `--tag <ref>` | No | OCI reference name (e.g., `myregistry.io/myvm:latest`) |

### 3.2 Build Steps

```
Cloud Image (qcow2/raw)
    |
    v
1. Mount read-only via guestfish
    |
    v
2. Detect kernel in /boot (see S3.3)
    |
    v
3. Detect matching initrd in /boot (see S3.3)
    |
    v
4. Extract kernel + initrd -> kernel layer tar archive
    |
    v
5. Read root partition PARTUUID from GPT
   (guestfish part-get-gpt-guid /dev/sda 2)
    |
    v
6. Extract remaining rootfs (excluding /boot/vmlinuz-*, /boot/initrd*)
   -> rootfs layer tar
    |
    v
7. Build OCI config blob with kernel_cmdline, paths, PARTUUID
    |
    v
8. Assemble OCI manifest and push to local store
```

Step 5 uses `guestfish part-get-gpt-guid /dev/sda 2` to read the existing PARTUUID from the cloud image's GPT partition table. This PARTUUID is stored in the config blob and used in the kernel cmdline for device-name-independent root device identification.

### 3.3 Kernel Detection Logic

The build process must locate the highest-version kernel and its matching initrd from the cloud image's `/boot` directory:

```
1. List /boot/vmlinuz-* (or /boot/vmlinuz if no versioned files; ARM: /boot/Image)
2. Sort by version number (e.g., 5.15.0-100 > 5.15.0-91), pick highest
3. Match initrd by same version suffix:
   - /boot/initrd.img-{version} (Debian/Ubuntu)
   - /boot/initramfs-{version}.img (RHEL/Fedora)
4. Error if no kernel found: "no kernel found in /boot; cloud image may not be bootable"
```

The version sorting uses numeric comparison on each segment separated by `.` and `-`, so that `5.15.0-100` correctly sorts higher than `5.15.0-91`.

### 3.4 PARTUUID Strategy

The root partition is identified by PARTUUID rather than device name (e.g., `/dev/sda2`) to survive disk reordering across different VM configurations.

**GPT cloud images** (typical case):
- Read existing PARTUUID from cloud image GPT: `guestfish part-get-gpt-guid /dev/sda 2`
- Store PARTUUID in OCI config blob `rootfs_partuuid` field

**MBR-only cloud images** (legacy):
- Convert partition table from MBR to GPT first
- Set a fixed PARTUUID via `guestfish part-set-gpt-guid /dev/sda 2 <uuid>`
- Proceed as above

**Rationale**: `root=PARTUUID=<uuid>` is device-name-independent. Unlike `/dev/sda2` or `/dev/vda2`, a PARTUUID remains stable regardless of how the hypervisor enumerates disks.

**Note on virtiofs path**: The OCI virtiofs boot path does **not** use PARTUUID -- there is no block device. The guest kernel mounts the root filesystem via `root=cocoonfs rootfstype=virtiofs`, which references the virtiofs tag rather than a partition UUID. However, the build process still records the cloud image's PARTUUID in the config blob `rootfs_partuuid` field. This preserves the option to fall back to block-device boot (e.g., qcow2 reconstruction) without requiring a rebuild.

## 4. User Customization (`Cocoonfile`)

### 4.1 Syntax

Cocoonfile uses Dockerfile-like syntax for familiarity:

```dockerfile
FROM cocoon.io/ubuntu:22.04
RUN apt-get update && apt-get install -y nginx
COPY ./app /opt/app
EXPOSE 80
```

The `FROM` directive references a previously built OCI VM image (not a standard container image). Subsequent instructions modify the rootfs layer to produce a customization layer.

Each Cocoonfile build adds **one** customization layer on top of the existing layers. Multiple Cocoonfile builds can be chained: the output of one build (with its customization layer) becomes the `FROM` base for the next build, accumulating layers 3, 4, 5, etc. This enables composable image pipelines where a shared middleware layer is built once and team-specific application layers are added on top.

### 4.2 Build Mechanism

The Cocoonfile build process leverages existing container build infrastructure:

1. Parse Cocoonfile using Docker/BuildKit Go libraries (`github.com/moby/buildkit`)
2. Mount the rootfs layer and any existing customization layers (from the base OCI VM image) as the build context base filesystem
3. Execute `RUN`, `COPY`, `ADD`, and other Dockerfile instructions against the mounted rootfs
4. Compute the delta (changed files) between the original filesystem state and the modified state
5. Package the delta as a new customization layer with media type `application/vnd.cocoon.vm.rootfs.v1.tar`

The kernel layer (layer 1) and all preceding layers are carried forward unchanged from the base image. Only the new customization layer is created.

### 4.3 Dependencies

Building Cocoonfile support requires additional Go module dependencies:

| Module | Purpose |
|--------|---------|
| `github.com/google/go-containerregistry` | OCI manifest/layer manipulation, registry push/pull |
| `github.com/moby/buildkit` | Dockerfile parsing and instruction execution |

**Current state**: The project's `go.mod` currently includes `github.com/docker/go-units` only. The two modules above must be added for OCI VM image support.

## 5. Pull Process (`cocoon image pull --oci`)

### 5.1 Registry Pull

1. Pull the OCI manifest from the registry using `go-containerregistry`
2. Verify that layer media types match the expected cocoon VM types (see [section 2.1](#21-media-types))
3. Pull layers by digest -- registry deduplication ensures shared layers are transferred only once

If media type verification fails, the pull aborts with a permanent error indicating the image is not a valid Cocoon OCI VM image.

### 5.2 Local Cache Extraction

After pulling, layers are extracted into a local cache directory keyed by manifest digest:

```
{cache}/oci/{manifest-digest}/
+-- manifest.json
+-- config.json
+-- vmlinuz          # From kernel layer
+-- initrd.img       # From kernel layer
+-- rootfs/          # Rootfs layer extracted as directory tree
+-- custom-1/        # First customization layer (if present)
+-- custom-2/        # Second customization layer (if present)
+-- ...              # Additional customization layers as needed
```

The kernel and initrd are extracted as standalone files (not inside a tar) for direct use by Cloud Hypervisor's `payload.kernel` and `payload.initramfs` fields. The rootfs and customization layers are extracted as directory trees (not kept as tars) for use as OverlayFS lowerdirs. Customization directories are numbered in layer order: `custom-1/` corresponds to OCI layer 3, `custom-2/` to layer 4, and so on.

### 5.3 Layer Extraction

Layers are extracted as directory trees for OverlayFS composition. No qcow2 reconstruction, guestfish, or qemu-img is required:

```
1. Extract kernel layer tar -> vmlinuz + initrd.img (standalone files)
2. Extract rootfs layer tar -> rootfs/ directory tree
3. For each customization layer (in order):
   Extract customization tar -> custom-{N}/ directory tree
```

All extracted directories in the cache are **read-only** and **shared** across VMs. Per-VM copy-on-write is handled by OverlayFS at boot time (see [section 8](#8-storage-layout)).

When composing the OverlayFS stack, the `lowerdir` parameter lists directories from top to bottom (rightmost is lowest):

```
lowerdir=custom-N:...:custom-2:custom-1:rootfs
```

For example, an image with two customization layers:

```
lowerdir=custom-2:custom-1:rootfs
```

All customization directories and the rootfs directory are read-only lowerdirs. File lookups proceed from left to right: a file in `custom-2` shadows the same path in `custom-1`, which shadows the same path in `rootfs`.

### 5.4 Cache Key

The OCI manifest digest serves as the cache key:

- Re-pull with the same digest results in a cache hit; layer extraction is skipped entirely
- Cache invalidation happens only when the manifest digest changes (i.e., any layer was modified)
- The cache directory structure under `{cache}/oci/{manifest-digest}/` is self-contained (directories, not qcow2 files) and can be garbage-collected independently

## 6. Boot Process (Direct Kernel + virtiofs)

### 6.1 Cloud-Hypervisor REST API Payload

For OCI VM images, Cocoon uses **direct kernel boot** via Cloud Hypervisor's `payload.kernel` field and **virtiofs** for the root filesystem. The CH REST API requires both the `payload` (kernel/initrd/cmdline) and `fs[]` (virtiofs configuration):

```json
{
  "payload": {
    "kernel": "/var/lib/cocoon/cache/oci/{digest}/vmlinuz",
    "initramfs": "/var/lib/cocoon/cache/oci/{digest}/initrd.img",
    "cmdline": "root=cocoonfs rootfstype=virtiofs rw console=ttyS0,115200n8 console=hvc0"
  },
  "fs": [
    {
      "tag": "cocoonfs",
      "socket": "/var/lib/cocoon/vms/{vmID}/virtiofsd.sock",
      "num_queues": 1,
      "queue_size": 1024
    }
  ]
}
```

The `cmdline` value is read from the OCI config blob's `kernel_cmdline` field. The `kernel` and `initramfs` paths point to the extracted files in the OCI cache directory. The `fs[]` entry configures virtiofs to serve the OverlayFS-merged root filesystem to the guest.

### 6.2 virtiofsd Lifecycle

Before issuing the Cloud Hypervisor VM create/boot API call, Cocoon must spawn a `virtiofsd` process for the VM:

1. Mount OverlayFS for the VM (see [section 8](#8-storage-layout) for the mount command)
2. Spawn `virtiofsd` with `--shared-dir` pointing to the merged mount point and `--socket-path` matching the `fs[].socket` in the CH config
3. Wait for the virtiofsd socket to become available
4. Issue the CH REST API `vm.create` + `vm.boot` calls

The virtiofsd process runs for the lifetime of the VM and is terminated when the VM is stopped or deleted. See [docs/17-volume-passthrough.md](./17-volume-passthrough.md) for virtiofsd lifecycle management details.

### 6.3 No Firmware Required

Direct kernel boot bypasses UEFI entirely:

- **No `CLOUDHV.fd` needed**: The firmware file is not loaded, not referenced, and does not need to be present on the system for OCI VM images.
- **Faster boot**: The kernel loads immediately without firmware initialization, UEFI variable storage setup, or bootloader chain (UEFI -> GRUB -> kernel).
- **No block device for rootfs**: The root filesystem is served via virtiofs from the host OverlayFS mount, eliminating the need for qcow2 disk reconstruction.
- **Kernel + initrd sourced from OCI cache**: The kernel and initrd come from the OCI kernel layer, not from a disk image's `/boot` directory.

### 6.4 Boot Detection

Boot detection for OCI VM images uses the **same serial log pattern matching** as firmware-booted VMs:

- Login prompt detection via serial console output (`login:` pattern)
- The `--boot-timeout` flag applies identically -- if the login prompt is not detected within the timeout period, the boot is considered failed

No changes to the boot detection logic are required. The detection mechanism is agnostic to how the kernel was loaded (firmware vs. direct).

## 7. CLI Changes

### 7.1 New and Modified Commands

| Command | Description |
|---------|-------------|
| `cocoon create --oci <ref>` | Create VM from OCI VM image |
| `cocoon run --oci <ref>` | Create and start VM from OCI VM image |
| `cocoon image build <cloudimg> [--tag <ref>] [--file Cocoonfile]` | Build OCI VM image from cloud image |
| `cocoon image pull --oci <ref>` | Pull OCI VM image from registry |
| `cocoon image push --oci <ref>` | Push OCI VM image to registry |

### 7.2 Flag Semantics

The `--oci` flag explicitly selects the OCI VM image code path:

- **With `--oci`**: Image reference is resolved as an OCI VM image. Boot strategy is automatically set to direct kernel boot. No firmware is loaded.
- **Without `--oci`**: Image is treated as a direct cloud image (qcow2/raw) or URL. Boot strategy is automatically set to UEFI. `CLOUDHV.fd` firmware is loaded.

The boot strategy is **auto-determined** based on the presence of `--oci`. There is no user-facing `--boot-strategy` flag.

## 8. Storage Layout

```
/var/lib/cocoon/
+-- cache/
|   +-- images/              # Existing: qcow2 base images (non-OCI path)
|   +-- oci/                 # NEW: OCI VM image cache
|   |   +-- {manifest-digest}/
|   |       +-- manifest.json
|   |       +-- config.json
|   |       +-- vmlinuz        # Extracted kernel
|   |       +-- initrd.img     # Extracted initrd
|   |       +-- rootfs/        # Rootfs layer (extracted directory tree, read-only)
|   |       +-- custom-1/      # First customization layer (read-only, if present)
|   |       +-- custom-2/      # Second customization layer (read-only, if present)
|   +-- manifests/           # Existing: OCI manifest cache
+-- firmware/                # Existing: CLOUDHV.fd (UEFI only, not used by OCI path)
+-- vms/
    +-- {vmID}/
        +-- upper/           # NEW: OverlayFS upperdir (per-VM COW writes)
        +-- work/            # NEW: OverlayFS workdir (kernel internal)
        +-- merged/          # NEW: OverlayFS mount point -> virtiofsd serves this
        +-- virtiofsd.sock   # NEW: virtiofsd socket for this VM
```

The OverlayFS mount command for a VM with two customization layers:

```bash
mount -t overlay overlay \
  -o lowerdir=/var/lib/cocoon/cache/oci/{digest}/custom-2:/var/lib/cocoon/cache/oci/{digest}/custom-1:/var/lib/cocoon/cache/oci/{digest}/rootfs,\
upperdir=/var/lib/cocoon/vms/{vmID}/upper,\
workdir=/var/lib/cocoon/vms/{vmID}/work \
  /var/lib/cocoon/vms/{vmID}/merged
```

Key points:

- The `cache/oci/` directory is new. Each subdirectory is named by the OCI manifest digest and contains all extracted artifacts for that image as directory trees (not qcow2 files).
- `rootfs/` and `custom-{N}/` directories are read-only and shared across all VMs created from the same OCI image. No per-VM duplication of base image data.
- `vmlinuz` and `initrd.img` are stored alongside the rootfs directories and are referenced directly by Cloud Hypervisor's `payload.kernel` and `payload.initramfs` fields.
- Per-VM state under `vms/{vmID}/` includes OverlayFS directories (`upper/`, `work/`, `merged/`) that provide copy-on-write semantics. Guest writes land in `upper/`, leaving the shared cache untouched.
- The `virtiofsd.sock` socket is the communication channel between Cloud Hypervisor and the virtiofsd daemon serving the merged filesystem.
- The existing `cache/images/`, `cache/manifests/`, and `firmware/` directories are unchanged.

## 9. Boot Strategy Simplification

With OCI VM images, the boot strategy model is simplified to two modes, auto-selected based on image source:

| Image Source | Boot Strategy | Firmware | Kernel Source | Rootfs | Selection |
|---|---|---|---|---|---|
| Cloud image (qcow2) | UEFI | CLOUDHV.fd (`payload.firmware`) | From disk (UEFI loads grub/kernel) | qcow2 block device | Auto: no `--oci` flag |
| OCI VM image | Direct + virtiofs | None | From OCI layer (`payload.kernel`) | virtiofs root (OverlayFS merged) | Auto: `--oci` flag present |

### 9.1 Changes to Boot Strategy Types

- `BootStrategyPVH` is **removed entirely**. PVH boot was an alternative firmware-based approach that added complexity without sufficient benefit over UEFI for the cloud image path.
- The `BootStrategy` type becomes a two-value enum: `"uefi"` | `"direct"` (internal only, auto-selected based on `--oci` flag).
- No user-facing `--boot-strategy` flag is needed. The choice is implicit:
  - `cocoon create myimage.qcow2 ...` uses UEFI
  - `cocoon create --oci myregistry.io/myvm:latest ...` uses direct kernel boot

### 9.2 Rationale

The two boot strategies map cleanly to the two image sources. Users do not need to understand boot strategy internals -- they choose an image format, and the boot method follows automatically.

## 10. Kernel Pinning (Trade-off)

### 10.1 Design Decision

**Kernel version is locked at `cocoon image build` time.**

The kernel used to boot the VM comes from the OCI kernel layer, which was extracted from the cloud image during `cocoon image build`. It does **not** come from the rootfs disk image's `/boot` directory.

### 10.2 Implications

- Guest-side `apt upgrade linux-image-*` installs a new kernel to the rootfs `/boot` directory but has **no effect** on boot. The VM continues to boot with the kernel from the OCI kernel layer.
- To upgrade the kernel: re-run `cocoon image build` with an updated cloud image. This produces a new kernel layer with the updated kernel.
- This matches the **container model**: images are immutable artifacts. Upgrade means rebuild and redeploy, not in-place mutation.

### 10.3 Benefits

- **Reproducibility**: The kernel version is deterministic for a given OCI manifest digest. Two VMs created from the same OCI VM image always boot the same kernel.
- **Auditability**: The kernel version can be inspected from the OCI manifest without booting a VM. `cocoon image inspect --oci <ref>` can report the exact kernel version.
- **Rollback safety**: Rolling back to a previous OCI VM image version also rolls back the kernel, eliminating kernel/userspace version skew.

## 11. Compatibility Matrix

| Source Image | Boot Method | Firmware | Kernel Source | Rootfs Delivery | Registry |
|---|---|---|---|---|---|
| Cloud image (qcow2/URL) | UEFI | CLOUDHV.fd | Loaded from disk by bootloader | qcow2 block device | N/A |
| OCI container image | UEFI | CLOUDHV.fd | Loaded from disk by bootloader | qcow2 (converted from rootfs) | Container registry |
| OCI VM image (this doc) | Direct kernel + virtiofs | None | Extracted from OCI kernel layer | virtiofs (OverlayFS merged from layers) | Container registry |

**Row 1** (Cloud image): The existing default path. Users download a cloud image, Cocoon boots it via UEFI. No registry involved.

**Row 2** (OCI container image): The [docs/04](./04-oci-conversion.md) pipeline. Cocoon pulls a container image, converts it to qcow2, boots via UEFI. Requires a bootloader (GRUB) pre-installed in the container image.

**Row 3** (OCI VM image): This document. Cocoon builds or pulls an OCI VM image with separate kernel/rootfs/customization layers, extracts them as directories, composes them via OverlayFS, and serves the merged filesystem to the guest via virtiofs. Direct kernel boot, no bootloader or block device required.
